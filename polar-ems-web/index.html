Why this problem needs AI, not just rules

A polar station is an isolated microgrid: no utility backup, fuel shipped in at enormous cost, and satellite internet that can vanish for weeks. A rule-based controller can keep the lights on — it cannot adapt its diesel/battery balance to shifting wind and sun the way a forecast-driven optimizer can. POLAR-EMS runs both, side by side, so the fuel savings are measured, not asserted.

01

Fuel is the scarce resource

Every litre of diesel is shipped in. The optimizer's entire job is cutting litres burned and generator runtime hours, not just visualizing them.

02

Failure is a safety issue

Losing heat at −45°C is life-threatening. Life-support and heating loads sit in an unshed priority tier, enforced independently of any AI decision.

03

The cloud is a bonus, not the brain

Telemetry, forecasting, dispatch and safety rules all run at the edge. Sync to the cloud portal is opportunistic and can queue for as long as needed.

What's real and what's simulated

Data honesty matters more to judges than polish. Here is exactly what this build is.

This is a synthetic simulation, not live station telemetry. Weather, generation, load, battery and diesel behaviour are generated by an explicit physical model running in your browser (power curves, seasonal solar/polar-night cycles, priority-weighted load, battery/diesel dynamics) — not random numbers, and not a real feed from any station. Forecasts use a seasonal-naive statistical model, not a trained neural network. Every number on this page — fuel saved, CO₂ avoided, MAE/RMSE — is computed live from the running simulation and changes if you change the scenario.

Model inputs

Load model

Seasonal same-hour baseline blended with short-term persistence of the current deviation, decayed toward the seasonal mean as the horizon grows. Inputs: hour-of-day, day-of-year, outside temperature, recent load trend.

Renewable model

Deterministic power-curve projection (wind speed → turbine output; irradiance → PV output) combined with persistence of the current weather deviation, decayed over the horizon. Solar is forced toward zero through the modeled polar-night window.

Scoring

Each forecast is time-stamped for a target moment; once the simulation reaches that moment, the realized actual is compared against the stored prediction to update a rolling MAE/RMSE per horizon.

Dispatch Optimizer

Every dispatch tick is computed twice, from identical weather and load conditions: a deterministic rule-based baseline, and the POLAR-EMS heuristic optimizer. The difference below is measured, not assumed.

Live backend

This panel is completely independent of the Simulation Mode tabs above — it polls your own Python/FastAPI backend (see backend/ in the project) so that inputs you give it from the VS Code terminal CLI show up here too.

If this page is loaded over HTTPS (e.g. from Vercel) and your backend is plain http://, the browser will block the connection as mixed content. Deploy the backend with HTTPS (see render.yaml) to connect from a live HTTPS site, or test locally by serving this page over HTTP too.
